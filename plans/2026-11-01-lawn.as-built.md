# As built: lawn

Built as planned, with no departures. A lens's notes now go where you'd write them, and
`e` opens the lens in your editor. `go test -count=1 ./...` passes. The agent-written
`dev-server` lens still resolves all 25 lines, unchanged.

## Chose: A note is the text after the reference, then the indented lines, as markdown
- where: `internal/site/lens.go`
- quote: `l.Items[i].Note = strings.TrimSpace(l.Items[i].Note + "\n\n" + n)`

**Because (Claude, not asked):** the plan didn't say how a same-line note and nested lines
combine. Keeping both, in reading order, loses nothing. Rendering the result as markdown
turns nested bullets into a list on the page, and a blank line between indented lines
makes a new paragraph. Before, notes were rendered inline, so a note now sits in its own
paragraph.

## Chose: `e` works on the lens list too
- where: `tui/app/lens.go`
- quote: `return m.editLens(s.lenses.Lenses[s.cur].File)`

**Because (Claude, not asked):** you often know which lens you want to write in before
opening it. Opening it first just to press `e` would be a step for nothing.

## Answered: A lens written as prompt prep reads back whole
**Answer (Claude, measured):** held, in a test and on the dev server. The test lens had an
intro, an item with a same-line note and nested bullets, a second paragraph indented
under them, a paragraph between items, and closing text. Every line came back where it
belonged: notes on their item, both prose paragraphs as the lens's closing, and nothing
as a stray item or dropped. The same shape with real references, served at
`lenses/zz-prep-check/`, showed it in the browser. The file was removed afterwards. The
TUI wasn't tried with a nested note at a narrow width, so how it wraps there is the next
thing Jeff will see.

# `phoropter`: one command, run inside a repository, that indexes, builds and serves

Today phoropter is three invocations you have to know: `node src/build.ts <repo>
[commit]`, `node src/serve.ts <repo> [commit] --port …`, and nothing at all for keeping
indexes, which are rebuilt from scratch every time. This plan makes it one command,
`phoropter`, that you run inside a repository. It's the first of the plans toward a
`phoropter` CLI. Plugins for indexers and UIs, and how phoropter is installed, come
after.

It takes in the index store worked out with Jeff and shelved as `shelf/index-store.md`.
That plan couldn't land alone: its writing half was `phoropter index`, a command this
plan makes. Two plans that only work together are a distributed transaction, so they're
one plan now. Its decisions are restated here as Jeff answered them, and the seed is
deleted when this converts.

## Decision: `phoropter` with no arguments serves the repository you're in
- where: `src/serve.ts`
- quote: `// node src/serve.ts <repo> [commit] [--out site] [--port 4173]`

**Because (Claude, not asked):** the person reading plans is standing in the repository.
`phoropter` finds its root by walking up to `.git`, indexes what's missing into the
local cache, builds the site at `HEAD`, and serves it with the draft and notes in
`drafts/`, as the dev server does now. It prints the address. `phoropter <path>` does
the same for another repository, and `--at <commit>` serves another commit. Outside a
git repository, it says it reads one and stops. This is the experience the whole CLI is
for: "you run `ph` in the repo" (Jeff). Every other command is secondary to it.

For now it opens nothing; it prints the address. Jeff thinks a UI is the right default,
with the address shown so it can be handed to the agent, and that closing the UI could
stop the server. Both depend on what "a UI" is, so they're the plugin plan's to decide,
and they're written into its seed (`shelf/ui-plugins.md`). This plan is whole without
them: a server and its address are a complete thing. A later plan that opens a UI adds
to it and leaves nothing broken here.

## Decision: The port is 4173, or the next free one
- where: `src/build.ts`
- quote: `options: { out: { type: 'string', default: 'site' }, port: { type: 'string', default: '4173' } },`

**Because (Claude, measured):** this pair already serves two repositories at once
(mock-control on 4173, phoropter on 4175), and choosing a port by hand each time is
friction. If 4173 is taken, `phoropter` takes the next free port and prints it. `--port`
still pins one.

## Decision: `phoropter url` says where the server is, for the agent and the UI
- where (new): `src/cli.ts`

**Because (Jeff, then Claude):** "the address displayed somewhere so it can be handed to
the agent. Is there a better way to do that?" Taking the next free port means nobody can
guess the address anymore, and that gap would be this plan's own. So while it serves,
`phoropter` records the address, the repository's root, the commit and its process in a
small file outside the repository, under the cache directory, keyed by the root. It
removes the file when it stops. `phoropter url`, run anywhere in the repository, prints
the address of the server for it, or says none is running. CLAUDE.md can tell an agent
to run it, and a UI can show it. Writing outside the repository keeps phoropter a reader
of it.

## Decision: A repository with no plans gets a welcome, not an error
- where: `src/render.ts`
- quote: `<p>No plans in <code>plans/</code> at this commit.</p>`

**Because (Jeff):** "what if there are no plans?" It's how every repository starts. The
site still builds: the home page says there are no plans yet, links the guide's first
section ("Write the plan"), and says where a draft would go. The guide is served on
every site already (twill). Phoropter doesn't create `plans/` or a first draft: that's
`init`, and phoropter only reads. Jeff's idea for `init` is that the first draft is about
how the pair works together, with the defaults as its prompts' fallbacks ("the agent
always asks before converting a plan to code", defaulting to no). It's in `init`'s seed.
`init` is a write, so it belongs to the UI side. When it exists, the welcome page points
to it. Until then the welcome is whole on its own.

## Decision: `phoropter build` writes the static site, as `build.ts` does
- where: `src/build.ts`
- quote: `// node src/build.ts <repo> [commit] [--out site]`

**Because (gimlet):** a static site generator plus a dev server, not a running API. The
built site stays a function of one commit, for publishing or reading from `file://`, and
never holds a draft or notes. `phoropter build` takes the same `<path>`, `--at` and
`--out`, and uses the same index store, so a second build of the same commit doesn't
re-index.

## Decision: Indexes are facts about commits, stored apart from pages
- where: `shelf/index-store.md`
- quote: `# Seed: indexes are facts about commits, kept apart from pages`

**Because (Jeff and Claude, from the index store):** three layers. Plans are testimony,
committed and never edited. Indexes are facts about commits that never change. Pages
are a cheap projection of the two, never committed. Gimlet's reasons not to commit the
site hold, and two more came up: a committed site is always one commit behind, and the
"now" column changes nearly every page on every commit. The expensive, fragile part was
never the pages. It's indexing old commits, whose toolchains may be gone.

- **Each index is stored per commit, package, and indexer with its version,** and never
  changes. Phoropter keeps only what it reads (each definition's symbol, file and line
  range), as JSON, not the raw `.scip`. Measured on mock-control at `f02528f`: 185
  definitions from about 970 lines of TypeScript make 29.7 KB of JSON, 2.5 KB compressed
  as git stores it, indexed in under half a second. That's about 30 bytes of JSON per
  line of source. The file leaves out its commit (the path has it) and sorts its keys,
  so a package that didn't change between two plan commits gives byte-identical files,
  which git stores once.
- **The indexes plans need are committed,** in `.phoropter/index/<sha>/<package>.json`,
  like a lockfile. That way a plan's symbol anchors outlive their toolchain. Per branch
  is safe: keyed by sha, merges only add directories, and an index survives a squash
  merge that loses its commit. A cache outside the repository and git notes were weighed
  and set aside (Jeff).
- **The index for now lives in a local cache,** `$XDG_CACHE_HOME/phoropter/` or
  `~/.cache/phoropter/`, under the same key. It moves with every commit, so committing it
  would be the churn gimlet avoided.
- **A build indexes only what's missing,** from the store and then the cache (Jeff: "index
  the missing pieces"). The draft, re-read on every request, reads the same store, so a
  refresh doesn't wait on an indexer.
- **A missing indexer is a view status, `no-index`,** naming the indexer it needed, and
  never a failed build. The profile defines it.

## Decision: `phoropter index` is the one command that writes into the repository
- where: `src/scip.ts`
- quote: `export function indexCommit(repo: Repo, sha: string, packages: Set<string>): Map<string, Definition> {`

**Because (Jeff):** a build never writes into the repository it reads. Loden says
"Phoropter only reads", and gimlet made the site "never a place to write." `phoropter
index` writes the indexes plan commits need into `.phoropter/index/`, from the cache or
by indexing, because a person ran it to do exactly that. It writes nothing else, and
git shows the new files to commit. A build that found plan commits only in the cache
says so, and names the command ("safest for now", Jeff).

## Decision: `package.json` names the command, and the npm scripts stay
- where: `package.json`
- quote: `"dev": "node src/serve.ts ../mock-control 90c65b9",`

**Because (Claude, not asked):** a `bin` entry makes `phoropter` a command in this
repository (`npx phoropter`) and anywhere after `npm link`, since Node 24 runs the `.ts`
sources directly. How phoropter is installed for other people is the shipping plan's
question. `npm run dev` stays as it is, serving mock-control at an old commit for the
tests and for Jeff's habit.

## Decline: Opening a UI or a browser, in this plan
**Because (Claude, not asked):** what to open is a choice between UIs, and UIs as
plugins is the next plan, with Jeff's ideas for it in its seed. Until then, the address
is printed, and `phoropter url` finds it again.

## Decline: Watching the repository and rebuilding as commits land
**Because (Claude, not asked):** the site is a function of one commit (gimlet), and the
working tree's draft and notes are already re-read on every request. A new commit is a
new `phoropter`. A watcher may earn a plan once there's a reason, not before.

## Guess: Someone new to a repository is reading its plans within a minute of `phoropter`
**Disproved if:** on a fresh clone of mock-control or this repository, with the committed
index store in place, `phoropter` takes more than a minute to print its address, or
prints anything that has to be read twice.

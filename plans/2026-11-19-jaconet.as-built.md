# As built: jaconet

Built as planned. `Show` and `Resolve` go through one `git cat-file --batch`, and a
build of phoropter's repository went from 750 git processes to 116, and from 5.5s to
about 1.1s warm. Served, the first request after a commit went from 5.3s to 1.73s,
measured three times on a clone with a commit before each. `go test -count=1 ./...`
passes. `internal/site`'s tests went from 29s to 15s, since they build sites too.

The plan's second Decision was wrong about its own numbers. It said the calls left as
commands were "a few dozen, a fraction of a second". After the change, 85 of the 116
remaining are `rev-parse --short`, from `Short`, and they're most of the second that's
left. The batch could answer them too, since its header line carries the full sha and
the short form is computable from it, but that's the "optimize it a little bit more"
sprint Jeff asked us not to start. If the Windows trial shows a wait, this is the first
place to look.

## Chose: An object that isn't a file is left to `git show`
- where: ``scip-go gomod github.com/hypertheory-labs/phoropter . `github.com/hypertheory-labs/phoropter/internal/site`/Repo#Show().``
- quote: `// A tree shows as a listing, not its raw object: leave it to git show.`

**Because (Claude, not asked):** `git show` of a directory prints a listing of its files,
and `cat-file` gives the raw tree object. Nothing in phoropter is known to show a
directory, but keeping the output the same by construction is cheaper than proving
nobody does. A name containing a newline, which the batch's protocol can't carry, goes
to the command too.

## Chose: A test kills the batch mid-session
- where: `internal/site/git_test.go`
- quote: `repo.batch.cmd.Process.Kill()`

**Because (Claude, not asked):** the plan promised that a dead batch costs a slow read,
not a wrong one. The test checks a file, a file that's missing, a directory, `HEAD`, and
a base written in prose. It checks them with the batch, after killing it, and with the
fresh batch that follows.

## Answered: A warm build of phoropter's repository takes under a second
**Answer (measured):** disproved, narrowly: 1.07s, 1.07s and 1.28s, from 5.46s, 5.52s
and 5.84s, at the same commit on the same machine. The rest is mostly `rev-parse
--short` (above).

## Answered: The site doesn't change by a byte
**Answer (measured):** held, apart from one line the guess should have left out. Sites
built at the same commit before and after the change were compared with `diff -r`, both
phoropter's and mock-control's. In each, one line differs, on the guide page: "From
phoropter, commit 9c2e415" before, and the new binary's commit after. That line names
the binary that built the site, so it has to change. Every other file is identical, and
the golden comparison passes.

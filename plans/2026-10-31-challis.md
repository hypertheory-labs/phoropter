# The plan list reads like the page: the draft first, then titles, newest first

The first aesthetics pass, from Jeff. The plan list leads with names like "ramie" and
"batiste", which are meaningless on purpose: the guide picks them so they can't turn
into categories. Phoropter's page leads with each plan's title and keeps the name in its
metadata line, and a projection of the page should keep the page's emphasis. The draft
is a row that's there only sometimes, and the list is oldest first. Ramie (reading the
draft) left how a draft looks to this pass.

## Decision: The draft has a slot at the top of the list, always
- where: `internal/tui/screens.go`
- quote: `row := ansi.Truncate("✎ draft     the plan being drafted, not committed", lw, "…")`

**Because (Jeff):** "high five." The draft is the thing being worked on now, so it gets
the top of the list, set apart in a bordered block rather than drawn as a row. With a draft it shows
the draft's title, when it was read, and how many prompts are open, which takes one more
fetch, of `draft/`. With none it says so: "No draft. When `plan.draft.md` exists, the dev
server shows it here." An empty slot also tells a newcomer drafts exist.

A built site never links a draft, even when there is one. The TUI runs in the repo, so
when there's no `rel="draft"` but `plan.draft.md` exists on disk, the slot says this
site doesn't serve drafts and the dev server does. That's a local fact, so it's the
TUI's to check.

## Decision: Plans are newest first, and `o` flips the order
- where: `internal/tui/screens.go`
- quote: `b.WriteString("\n" + styles.dim.Render("Oldest first, by the commit that added each plan."))`

**Because (Jeff):** the newest plan is usually the one you're asking about. The profile
orders plans by `added`, and the home page lists them oldest first, so newest first is
that order reversed. The order in use is named above the list. It isn't remembered
between runs: that would mean writing a settings file, and so far the TUI's only write
is a draft's notes. Settings may get their own plan someday, and the longer that waits,
the better the TUI has to be without them (Jeff).

## Decision: A plan is its title, with the name in a dim line under it
- where: `internal/tui/screens.go`
- quote: `row := ansi.Truncate(fmt.Sprintf("%s%-9s %s", mark, p.Name, p.Title), lw, "…")`

**Because (Jeff, then Claude):** "the names … are not very information bearing for
humans." Each plan takes two lines: its title, cut off with "…" at the pane's edge, and
under it, dim, `ramie · 2026-10-31 · 7 entries · ✓ as-built · revisits gimlet`. The
name stays, because plans refer to each other by name. Two lines halve how many plans
fit, about 15 in a usual terminal. Phoropter has 13 plans. When there are too many, the
answer is filtering, not names. All five go in the dim line for now, and it gets cut
back if it's cramped (Jeff).

## Decision: Breadcrumbs name a plan by its title
- where: `internal/tui/screens.go`
- quote: `func (s *docScreen) title() string {`

**Because (Claude, not asked):** the bar across the top is where a person sees where
they are, so it says what the plan is about: "phoropter-tui › Read the draft:
phoropter's edge…". Each crumb is shortened so the last one stays readable.

## Decision: A draft has an accent color, on its slot and its screen
- where: `internal/tui/styles.go`
- quote: `var styles = styleSet{`

**Because (Claude, not asked):** ramie kept a draft looking like a plan until this pass.
One color, used nowhere else, on the slot's border and on a draft's title bar, says
"not committed yet" before anything is read. The color is a terminal palette number, so
it follows the terminal's theme. Both the slot and the screen have it, so they read as
one thing (Claude, unanswered, so its fallback).

## Decision: The draft's About row says it takes a note on the whole draft
- where: `internal/tui/screens.go`
- quote: `text = "── About this draft"`

**Because (Jeff):** "I wish I could add a note that applies to the entire plan," written
as a note, while `a` on the About row already did exactly that. Nothing said so. The row
reads "About this draft · a to note it", and its pane ends with a line saying what `a`
does there.

## Decision: Text boxes wrap what's typed
- where: `internal/tui/form.go`
- quote: `b.WriteString("  " + ansi.Truncate(l, max(1, w-2), "…") + "\n")`

**Because (Jeff):** "this needs the multiline treatment as well," and "if there are a lot
of typos, it's because this note doesn't allow multiline". `enter` already starts a new
line, but a line longer than the pane was cut off with "…", so what was typed past the
edge couldn't be seen. The box wraps instead, and grows with what's in it.

## Decision: Layers have human names
- where: `internal/tui/screens.go`
- quote: `var layers = []string{"base", "as-built head", "generated"}`

**Because (Jeff):** "the 'generated' tag is a little clunky, I know what it means". The
profile's roles stay as they are in the data. The lens bar and help name the three
layers for a person, each with its commit beside it: before, as built, now. "Now" is
honest while the commit is beside it, and the help already explained "generated" as
"now". The other names weighed were then, landed, now, and at the plan, at the
as-built, at the site's commit (Claude, unanswered, so its fallback).

## Decline: Filtering and search in the plan list
**Because (Claude, not asked):** 13 plans fit. It's what comes when the list doesn't, and
then what fits best can be seen (Jeff).

## Guess: A person finds a plan by its title faster than by its name
**Disproved if:** Jeff finds himself scanning the dim lines for names, or finds the list
harder to read than before.

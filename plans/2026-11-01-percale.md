# Lenses: a reader's own subsets of plans, first version

A lens is a named list of plans and entries that one reader keeps: "auth", "bundling",
"what this work should keep in mind". Jeff's idea, worked through in `shelf/lenses.md`:
plans stay testimony, and a lens is a reader's way of looking at them. With a lens and a
kind filter, "what did we turn down in auth?" is one screen, not a search for a word the
plan may not use. For the course, a lens per topic is a teaching index into the
decisions.

This is the smallest version that shows whether Jeff reaches for lenses: a file format,
the dev server showing lenses, the TUI listing and filtering them, the agent writing them,
and Jeff adding to one from the TUI. File view (a lens made from a pasted path) comes
next, once two gaps are closed.

## Decision: A lens is a markdown file of references, the syntax `where:` already uses
- where (new): `drafts/lenses/<name>.md`

**Because (Jeff and Claude):** Jeff wants lenses portable: pasted into a ticket, or sent to
a coworker as "keep these earlier plans in mind". A list of references a person can read
without phoropter does that, and phoropter already resolves the syntax:

```markdown
---
repository: 1a2b3c4
---

# Auth

Everything the course has decided about sign-in, for the auth module.

- `plans/2026-10-31-batik.md › The index store is committed only by phoropter index`
- `plans/2026-11-01-poplin.md` — the whole plan
- `plans/2026-10-30-burlap.md › The verdict is the answer's first word…` — keep this in mind for grading
```

A whole plan or one entry per line. Text after the reference is a note to yourself. A
note has no state (no done, no date, no owner), so a lens can't turn into a backlog. `Y` in
the TUI already copies one line of this. `repository:` is the first commit's sha, which
every clone shares. When it doesn't match, phoropter says the lens came from another
repository and shows it anyway.

Lenses live in `drafts/lenses/` (Jeff chose it). It's already ignored by default and per
working tree, the dev server and the agent already read and write `drafts/`, and on a
branch it can be committed to share. Jeff's note: a lens always starts there, and saving
one to personal config, where it outlasts a fresh clone, is a later step someone takes on
purpose, the way work in progress becomes something kept.

## Decision: The dev server shows lenses, and a built site never does
- where: `internal/site/serve.go`
- quote: `if p == "/draft/" {`

**Because (Claude, not asked):** like the draft and notes, lenses are read from `drafts/` on
every request, so editing a file shows on the next refresh. `lenses/` lists them with how
many items each has. `lenses/<name>/` shows one: each item resolved to its entry, with
kind, title, plan, and for a guess its verdict or "open", plus the note. An item that
doesn't resolve is shown as written, saying so, never dropped. Everything is microdata in
the profile, so the TUI and the agent read the same page. A built site has no lenses: it
holds testimony, and a lens is someone's way of reading it.

## Decision: The TUI lists lenses, and filters one by kind
- where: ``scip-go gomod github.com/hypertheory-labs/phoropter . `github.com/hypertheory-labs/phoropter/tui/app`/listScreen#key().``
- quote: `case "enter", "l", "right":`

**Because (Jeff):** "the ability to have a subset and then just see 'waits'". `L` from the
plan list opens the lenses. A lens screen lists its items with their kind. `f` cycles a
filter: all, Decisions, Declines, open guesses (unanswered, or answered `not tested`).
`enter` opens the plan at the entry, and `y`, `Y` and `b` work as they do everywhere.
Filtering one page the TUI has read is a local fact, so it stays on the TUI's side of the
boundary.

## Decision: `+` adds what you're on to a lens
- where (new): `tui/app/lens.go`

**Because (Jeff, then Claude):** "mark this" should be one key from wherever you found it,
and Jeff wanted it in the first version: it "feels like collecting", and naming, notes and
the rest come later. So `+` on an entry or a whole plan asks only which lens, offering the
last one used, and appends the line. It asks for no note. Notes are written in the file,
by a person or the agent. Without `+`, only the agent and an editor would make lenses,
and the TUI would be read-only for the thing Jeff reaches for while reading. The TUI
writes the file directly, as it writes notes, and never edits a line already there, so a
lens someone pasted in stays as they wrote it.

## Decision: The agent block says how to make a lens
- where: `README.md › phoropter › Tell your agent`
- quote: ``- **Never edit a landed plan.** Changing an old decision is a revisit: a new plan, with``

**Because (Jeff):** "can you go 'mark' all the plans that seem to intersect with what we
are doing here". That's judgment by meaning, which is the agent's part, and it covers
what anchors can't: a new idea that bears on an old one with no shared code. The block
says: a lens is `drafts/lenses/<name>.md`, one reference per line, as `Y` copies them;
asked to mark plans, write or extend one and say what's in it and why; and when a lens
would help the two of you look at something, make one without being asked, and say so.
Jeff's note on that last part: an agent saying, unprompted, "I made a lens through which
we might look at this". His larger idea, that phoropter serves agent recipes like this
one the way skills work, belongs with the conventions in `init`, and is in
`shelf/init.md`.

## Decline: Showing which lenses hold an entry on its plan's page
**Because (Claude, not asked):** "you have a note about this" lighting up when you come
back to a plan is part of the idea. But it means every plan page reads every lens, and
the first version should find out whether lenses get used at all. The lens page already
shows the notes.

## Decline: File view's lens from a pasted path, in this version
**Because (Claude, not asked):** a lens of every plan touching a file needs the file's page
found from its path (`place-url-convention`) and the symbol anchors inside the file
listed on it (`symbol-file-unlinked`). Without those, the lens would miss every plan
anchored on a class in the file and look complete when it isn't. That's the next plan.

## Guess: An agent asked to mark plans writes a lens that resolves whole
**Disproved if:** asked to "mark the plans that bear on auth" (or any topic) in phoropter's
own repository, an agent writes a lens with any item the server can't resolve.

## Guess: Lens plus kind filter answers "why did we…" without grep
**Disproved if:** over a few days of course work, Jeff's "wait, why did we defer that?"
questions still send him (or the agent) to grep or a search more often than to a lens.

# Phoropter's Go indexer installs with `go install`

A `go install`ed phoropter finds no first-party indexers (organdy's as-built), and
`phoropter doctor` now says so plainly, but it can't fix it. The indexers live in
`indexers/`, run from a clone through `indexer.json`. The Go one's module is named
`phoropter-index-go`, so `go install` can't fetch it by name. This is the second thing
between the trial and a newcomer (`shelf/order.md`). The trial's project is TypeScript,
so this plan says plainly what it does for TypeScript: not yet.

## Decision: The Go indexer moves to `cmd/phoropter-index-scip-go/`, in phoropter's module
- where: `indexers/go/go.mod`
- quote: `module phoropter-index-go`

**Because (Jeff and Claude):** then `go install
github.com/hypertheory-labs/phoropter/cmd/phoropter-index-scip-go@latest` puts
`phoropter-index-scip-go` on `PATH`, where phoropter already looks for an indexer by
scheme (seersucker). That's no new discovery code, and it's one command `doctor` can
print. `go install` names a binary after its directory, so the directory carries the
scheme, the name discovery looks for. Jeff agreed: named for the scheme, not the
language. The `--describe` name stays `phoropter-index-go`. The indexer's dependencies
(the SCIP bindings, protobuf) join phoropter's `go.mod`; phoropter's own binary doesn't
link them. Three earlier anchors name `indexers/go/main.go` (two in seersucker's
as-built, one in grosgrain), and at HEAD they'll show the file gone. That's true: it
moved, and this plan is where to read why.

## Decision: A clone still finds it without installing
- where: `internal/site/indexers.go`
- quote: `if info, err := Describe(m.Command, dir); err == nil {`

**Because (Claude, not asked):** working on phoropter means editing the indexer and
running it at once. `indexers/go/indexer.json` stays, pointing at `go run
../../cmd/phoropter-index-scip-go`, so a binary built in the clone uses the clone's code,
as today.

## Decision: `doctor` says `go install` for Go
- where: `doctor.go`
- quote: `fix("phoropter's %s indexer is in a clone of phoropter: git clone https://github.com/hypertheory-labs/phoropter, "+`

**Because (Claude, not asked):** outside a clone, the fix for a missing Go indexer
becomes one line, the `go install` above, instead of "clone phoropter".

## Decline: Installing the TypeScript indexer, in this plan
**Because (Jeff and Claude):** it's Node, not Go, so `go install` can't carry it. The
choices are an npm package (`npx`, which means publishing to npm) or building it into
the Go binary, which can't run scip-typescript. Both are bigger than this plan. For the
trial, a TypeScript project, the indexer comes from a clone, and `doctor` says how. Jeff
agreed a clone is fine there: it tests `doctor`'s instructions honestly. And he put "one
more nickel toward 'or you can just `docker run` this thing'", because each language
adds a toolchain (.NET, Java next), and that's going to get weird. A container per
indexer is the one install shape that doesn't grow with them (`shelf/indexing.md`).

## Decline: Building the Go indexer into the phoropter binary
**Because (Claude, not asked):** organdy's as-built offered it as a fallback. It would
make Go work with no install at all, but it ties phoropter's release to the indexer's
and puts one indexer inside the thing every indexer is supposed to be outside of. The
contract stays honest when phoropter's own indexers are found the way anyone's are.

## Guess: A `go install`ed phoropter plus one more `go install` anchors Go symbols
**Disproved if:** on a machine with no clone, after the two `go install`s and scip-go,
`phoropter symbols` on a Go file fails, or `doctor` still reports the Go indexer missing.

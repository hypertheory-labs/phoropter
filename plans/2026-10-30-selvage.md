# Say in markup what the pages already say in prose

Phoropter-tui is the first reader of these pages besides a browser, and it reads nothing
else. Its brief to phoropter (`../phoropter-tui/docs/for-phoropter.md`) lists where it
had to parse prose or lean on a class name to get something the page already shows. This
plan closes the ones that need no decision about reasons, only markup and the profile.
Everything it adds is additive: nothing a reader uses today is renamed or reshaped, since
the rels and microdata are now a public API. The rest of the brief is on the shelf.

## Decision: A view lists each match as an item, with its lines
- where: `src/render.ts`
- quote: `<meta itemprop="matches" content="${v.matches}">`

**Because (phoropter-tui's brief):** "where in this excerpt is the quote?" is answered
today only by a `<mark>` and a note that says "quote at line 94" in prose: 28 views in
mock-control, 74 in phoropter. Each match becomes a `match` item with `startLine` and
`endLine`, one per match, since `matches` can be more than 1. The note stays, for people.

## Decision: Each excerpt's first line is a property beside it
- where: `src/render.ts`
- quote: `<pre itemprop="code" data-start="${h.start}">`

**Because (phoropter-tui's brief, then Claude, not asked):** a reader numbering an
excerpt's lines needs where it starts, and `data-start` and `span.ln` aren't in the
profile. A `codeStart` property, just before each `code` it describes. Microdata keeps
properties in document order, so the nth `codeStart` belongs to the nth `code`, and the
profile says so.

## Decline: Making each excerpt an item holding its own start and code
**Because (Claude, not asked):** it's the cleaner shape, but `code` would stop being a
property of the view and of the place, and phoropter-tui reads it there. The paired
property gets the same information out without moving anything a reader already uses.

## Decision: The home list marks up its as-built and revisits links, and counts entries
- where: `src/render.ts`
- quote: ``const asBuilt = p.asBuilt ? `, with <a href="${rel(here, p.asBuilt.href)}">an as-built</a>` : '';``

**Because (phoropter-tui's brief):** "which plans are done, and which revisit something?"
shouldn't need opening each plan. The plan page already has `rel="as-built"
itemprop="asBuilt"` and `rel="revisits" itemprop="revisits"`; the home list gets the
same. "9 entries" gets `entryCount`, on plans and places both.

## Decision: `new` has one shape
- where: `src/render.ts`
- quote: `${anchor.isNew ? ', <span itemprop="new">new</span>' : ''}`

**Because (phoropter-tui's brief):** on an anchor it's `<meta content="true">`, on a
place page's item it's the text "new". Both become the meta, with "new" still shown on
the place page.

## Decision: The profile says `base` and `head` can be text
- where: `src/render.ts`
- quote: ``return `<span itemprop="base">${esc(plan.beforeText || 'not given')}</span>`;``

**Because (phoropter-tui's brief, then Claude, not asked):** gimlet's base is "none, a
new repo", and the guide now says a squashed `head:` can stop being a commit. Both are
written as they are. The profile says a `base` or `head` is a `<data>` with the full sha
when it's a commit here, and the text as written otherwise.

# Work in progress gets its own folder: the draft, and requests to revisit landed plans

Loden (the edge: one draft plan, served live) put the draft at the repository's root,
so anyone opening the repository sees whether a plan is being drafted. Since then two
things moved. First, nankeen (landed plans aren't edited from the TUI) declined editing,
and Jeff named what he wants instead: "a way to indicate [past plans] need revisited.
Maybe with some notes." Those notes need a home, and it isn't `plans/`. Second, Jeff
said where that home is: "this is just one developer's idea here about something", and
its value would be "look at my branch, here's what I'm thinking about this old plan."
The revisit is how main deals with it.

Asked in loden's frame: is the root still the right place for work in progress? What
moved is our understanding. Loden had one kind of work in progress, the draft. Now
there are two, and both are a person's thinking, not testimony. So `plans/` holds
testimony and nothing else, and everything still being thought about shares one folder.

This is the first plan that crosses the old line between phoropter and the TUI. It
changes the format, the dev server and the TUI in the same work.

## Decision: The draft, its notes, and requests on landed plans live in `drafts/`
- where: `src/draft.ts`
- quote: `export const DRAFT = 'plan.draft.md';`

**Because (Jeff):** "maybe we move to a '/plans-drafts/' directory, and the current plan
is in there, and any of these notes for old plans." The one draft is
`drafts/plan.draft.md`, and its notes are `drafts/plan.draft.notes.md`. Loden's rules
hold: one draft, one fixed name, nothing to configure. A top-level folder keeps what
loden wanted from the root: anyone opening the repository sees whether something is in
progress. It's called `drafts/` (Jeff). It's short, it says "not yet", and the guide
already calls a draft a draft. The requests in it are drafts of a different kind: a
person's case for a revisit, before anyone has written one. `plans.wip/` and
`plans-drafts/` were weighed. The name may become a seam for configuration someday, for
a repository that already has a `drafts/` (Jeff), but not now.

## Decision: A request to revisit is a notes file on a landed plan, kept in `drafts/`
- where: `plans/2026-10-31-nankeen.md › Editing a landed plan from the TUI`

**Because (Jeff, then Claude):** nankeen declined editing a landed plan. A note on one is
the conversation Jeff wanted instead of an edit. For `plans/2026-10-31-ramie.md`, the
request is `drafts/2026-10-31-ramie.notes.md`, in the annotating agreement's shape. Its
`annotates:` line names `plans/2026-10-31-ramie.md`, so it stands alone. A note quotes an
entry's heading, or has no quote and is about the whole plan.

The agreement puts notes beside their file, and these are in another folder. That's a
deliberate variation, with this reason: `plans/` holds testimony only. The guide says
so where it restates the agreement. A landed plan never changes, so its notes can't
come loose from what they quote, and they need no hash check.

## Decision: A revisit answers a request, and converting it deletes the request
- where: `plans/2026-10-31-loden.md › Converting a draft writes the plan and removes the draft`

**Because (Claude, not asked):** loden's conversion deletes the draft's notes, since what
mattered from them is in the plan's reasons by then. A request works the same way. The
agent drafts a revisit (`revisits:` the plan), and its intro cites the request. When the
revisit converts, the request it answers is deleted with the draft's own notes. If the
agent thinks the plan still holds, it says so in a note of its own in the request file.
The request stays until the person agrees, or a revisit lands anyway. The person can
always overrule the agent.

## Decision: Requests travel on branches, and main changes only by revisit
- where: `plans/2026-10-31-loden.md › Ignoring the draft in git is a suggestion, not a requirement`

**Because (Jeff):** "the supersedes thing is how we deal with it in main. I can even see
an ongoing branch called 'plans' where the lead developers do a lot of this." Loden made
ignoring the draft a suggestion, and that holds for all of `drafts/`. On a branch,
committing `drafts/` is how a teammate or a mentor reads a request or a draft before
anything is decided. On main, what lands is plans. The guide describes a long-lived
"plans" branch as one way a team can work, not a rule. Phoropter doesn't care which
branch it's on. In this repository, where Jeff and Claude work on main, `drafts/` is
ignored (Jeff). Here the pair is the team, a request is seen on the dev server and in the
TUI, and nothing in `drafts/` should land on main by accident.

## Decision: The dev server shows a plan's requests on the plan's page
- where: `src/serve.ts`
- quote: `function withDraftLink(html: string, here: string): string {`

**Because (Claude, not asked):** loden's ground holds: a built site is a function of one
commit and never shows `drafts/`, even when it's committed. The dev server shows work
in progress, so it adds a plan's requests to that plan's page as it serves it: the same
`annotation` items a draft has, after the entries they quote, and whole-plan notes
first. The home list marks a plan that has a request. The profile defines both.

## Decision: The guide and both CLAUDE.md files say where work in progress lives
- where: `guide.md`
- quote: ``A repository has at most one draft, `plan.draft.md` at its root.``

**Because (Claude, not asked):** the guide is the format, so it changes in the same work.
It gets the folder, requests and how a revisit answers them, and the notes-elsewhere
variation. The root CLAUDE.md tells the agent to look in `drafts/` for requests at the
start of a session and raise any it finds before other work. Otherwise a request is a
note in a drawer. The TUI's CLAUDE.md changes its draft paths.

## Decision: In the TUI, `a` on a landed plan writes a request
- where: `tui/internal/tui/screens.go`
- quote: `m.status = "only a draft takes notes; a plan is testimony"`

**Because (Jeff):** this is the feature nankeen pointed at. On a landed plan's entry, `a`
writes a note quoting its heading into the plan's request file. On its About row, `a`
writes a note on the whole plan. The plan's page names its file, so the TUI knows which
request file to write. The message on screen becomes "a plan takes notes, never edits".
The TUI reads requests back from the dev server's plan page, the same page the agent
reads, never from the file.

## Decision: The TUI finds the draft where the page says it is
- where: `tui/internal/notes/notes.go`
- quote: `func DraftOnDisk(dir string) bool {`

**Because (Claude, measured):** answering already opens the draft by the page header's
`file`, so it follows the move with no change. Checking for a draft the site doesn't
serve looks in `drafts/`. The TUI's sample draft is copied to `drafts/plan.draft.md`.

## Decline: Reading a draft from the root as well, for a while
**Because (Claude, not asked):** loden's reason for one fixed name was "nothing to
remember to pass." Two places to look is a second name to remember. No repository has a
draft at the root today, so nothing is stranded.

## Decline: A "needs revisit" flag without a note
**Because (Claude, not asked):** a flag with no reason is a backlog item. The note is the
flag, and it says what moved, which is the first thing a revisit needs.

## Guess: A request to revisit gets a draft back without being asked twice
**Disproved if:** a request sits in `drafts/` through a session that started with
CLAUDE.md's check, and nobody raises it.

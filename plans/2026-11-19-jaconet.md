# One git process for a build, not 750

The first request after a commit waits for the whole site to rebuild: 5.3s, twice, on
2026-11-19, and `phoropter build` takes 5.45s warm on phoropter's repository. Logging each
`git` call during a build shows where the time goes: 750 processes for 125 pages. 577
are `git show` (a file at a commit), 143 `rev-parse`, 29 `log`, 1 `ls-tree`. At about 7ms
to start each one, that's the wait. This is the first of the friction that stands
between a newcomer and their first round, though a newcomer's repository is small, and
they'll feel it least. It's first because it's measured, small, and changes nothing a
reader sees.

## Decision: A long-lived `git cat-file --batch` answers `Show` and `Resolve`
- where: ``scip-go gomod github.com/hypertheory-labs/phoropter . `github.com/hypertheory-labs/phoropter/internal/site`/Repo#Show().``
- quote: `out, err := r.git("show", sha+":"+path)`

**Because (measured, then Claude, not asked):** `git cat-file --batch` reads object
names on stdin and writes each object back, from one process. `<sha>:<path>` gives a
file's text, as `git show` does, and `<ref>^{commit}` resolves a ref to its commit, as
`rev-parse --verify` does. Missing objects say `missing`, which is how `Show` and
`Resolve` already report "not there". The `Repo` starts the process the first time it's
needed and keeps it, behind a lock, for as long as the `Repo` lives: one build, or a
server's session. It's still git reading the commit, so the site is still a function of
the commit alone.

## Decision: The other git calls stay as they are
- where: ``scip-go gomod github.com/hypertheory-labs/phoropter . `github.com/hypertheory-labs/phoropter/internal/site`/Repo#git().``
- quote: `cmd := exec.Command("git", append([]string{"-C", r.Dir}, args...)...)`

**Because (measured):** `log` (29 calls), `ls-tree` (1) and `rev-parse --short` together
are a few dozen processes, a fraction of a second. They don't fit the batch protocol,
and keeping them as commands keeps this plan to the part that's slow.

## Decision: If the batch process dies, the read falls back to a command
- where: ``scip-go gomod github.com/hypertheory-labs/phoropter . `github.com/hypertheory-labs/phoropter/internal/site`/Repo#Resolve().``
- quote: `out, err := r.git("rev-parse", "--verify", "--quiet", ref+"^{commit}")`

**Because (Claude, not asked):** a server runs for a session, and something can kill a
child process in that time. A slow read is better than a wrong page, so a read that
can't use the batch runs the command it replaces, and the next read starts a new batch.

## Decline: Caching file contents
**Because (measured, then Claude, not asked):** only 315 of the 577 reads are distinct, so
a cache would halve the reads. But with one process, a read costs microseconds, not a
process start, and a cache is state that has to be right about which commit it holds.
The batch alone should be enough. If the as-built says it isn't, a cache keyed by sha
and path can't go stale, since a commit never changes.

## Decline: An incremental rebuild
**Because (Jeff and Claude):** Jeff's idea: build once, then have each commit add what's
new and touch up the edges. Landed plans never change, so most pages would carry over.
But it gives the site state between builds, which is where wrong pages come from, and
the measurement says the time isn't in building pages. If the batch doesn't bring a
build under a second, this is the next thing to try.

## Decline: Reading git through a library (go-git, libgit2)
**Because (Claude, not asked):** go-git would remove the processes entirely, but it's a
large dependency, and its reading of a repository can differ from git's own. Phoropter
reads through git, so what it shows is what `git show` would. The batch keeps that.

## Decline: Settling poplin's swap in this plan
- where: `plans/2026-11-01-poplin.as-built.md`

**Because (Claude, not asked, then Jeff):** poplin's as-built proposed serving the old
site while the new one builds, and left it to Jeff. If this brings the first request
after a commit under a second, there's little left to swap for. Jeff: watch it. This is
a fast machine, and most will be slower; the Windows trial will say more. "I think we
want to avoid a bunch of 'let's optimize it a little bit more' sprints." If the wait is
a problem, we won't know for a while, and when we do, it gets a serious plan of its own.
The as-built reports the number.

## Guess: A warm build of phoropter's repository takes under a second
**Disproved if:** `phoropter build` on phoropter's repository, warm, takes more than a
second after the change. It took 5.45s before.

## Guess: The site doesn't change by a byte
**Disproved if:** a site built at the same commit before and after the change differs in
any file, or the golden comparison fails.

# The edge: one draft plan, served live, with its notes beside it

Jeff wants to question a plan before it's testimony, at the level of his understanding,
without that ever becoming an approval step. The hope reaches past this pair: a
developer on a branch can say "can you look over my plan?", and a senior or mentor's
feedback lands before the code exists, instead of in judgment at the code review.

So a repository has at most one draft, `plan.draft.md` at its root. Phoropter's dev
server shows it the way it shows a plan, with its anchors resolved, its open questions
and their fallbacks, and any annotations beside what they quote. When the pair is
confident, the draft becomes a plan in `plans/` and the draft is gone. Where the thinking before
the draft happened (a cart, a conversation, a whiteboard) is none of phoropter's
business.

It's a revisit of gimlet, phoropter's first version, which decided the site is a pure
function of one commit: "nothing goes stale; a page is only ever old," and every page
says its commit. A draft is uncommitted by nature. Asked in gimlet's frame: does a draft
belong on the site? What moved is our understanding: gimlet was about reading plans
that exist, and the edge is about the moment before one does.

## Decision: There is one draft, `plan.draft.md`, at the repository's root
- where: `guide.md › Working with plans › Drafts (optional)`

**Because (Jeff):** the highlander principle. A folder of `draft.drp`, `draft-2.drp`,
`final.drp`, `final-i-really-mean-it.drp` is what happens when drafts can pile up, and
a pile of draft plans is a backlog. One fixed name means anyone opening the repository
sees whether a plan is being drafted, and the dev server finds it without being told.
Its notes are `plan.draft.notes.md`, by the annotating agreement. Parallel work isn't
blocked: each branch or worktree has its own working tree, so it has its own draft. A
draft that wants to be two plans gets smaller: the rest waits wherever the pair keeps
such things (a cart's shelf, for a pair using carts) and is drafted after this one
converts.

Most plans are never drafts; they go straight to `plans/`. A draft is for when the
agent's confidence or the shared understanding is thin, or when the pair has agreed,
for a session, that the human sees every plan first: not to judge it, but to follow it.
Who decides that is the pair's to work out, not the format's.

## Decline: Naming a draft on the command line, `--draft <file>`
**Because (Jeff, then Claude):** it was this draft's first version, to keep carts out
of phoropter's code. A fixed name does that better: there's nothing to remember to
pass, and nothing to point at a cart. A flag like this is a configuration override, and
adding one now would be timid too early (Jeff); the convention should be solid first.

## Decline: More than one draft at a time
**Because (Jeff):** see the decision above. If a real case for two drafts in one
working tree shows up, that's a later plan, with the case in it.

## Decision: Ignoring the draft in git is a suggestion, not a requirement
- where: `.gitignore`
- quote: `.loom/cart/`

**Because (Jeff):** on a branch, committing the draft (and its notes) is how a mentor
reads it before the code: they check out the branch and run the dev server. Working
alone on a main line, there's no reason to commit it. People can figure out which they
are. Nothing breaks either way: `build.ts` reads only `plans/`, so a committed draft
never reaches a built site. This repository ignores `plan.draft.md` and
`plan.draft.notes.md`, since Jeff and Claude work on main.

## Decision: Converting a draft writes the plan and removes the draft
- where: `guide.md › Working with plans › Drafts (optional)`

**Because (Jeff and Claude):** a draft doesn't need a name or a date until it's a plan,
and the guide's date is "the day you say we're implementing this," which is the moment
of converting. Converting writes `plans/YYYY-MM-DD-<name>.md`, folds each answer into
its entry's reason, labels a fallback that became the decision (`Claude, unanswered,
so its fallback`), drops the prompts and the draft comment, and deletes
`plan.draft.md` and its notes. When the pair has enough confidence, the draft converts
whether or not every prompt is answered, since silence means proceed. Usually the
agent says it's ready, and either can; whoever wrote the draft converts it, usually the
agent. Phoropter only reads. Some will push back on converting with prompts open;
we're keeping it (Jeff).

The notes are deleted, not kept. A draft's annotations are mostly the questions a human
asked to get their understanding lined up, and those don't need a record (Jeff). What
mattered from them is in the plan's reasons. On a branch where the draft was committed,
git keeps them anyway.

## Decision: The static site stays a function of the commit; only the dev server shows the draft
- where: `src/serve.ts`
- quote: `const { pages, title } = build(args.repo, args.ref, args.out);`

**Because (Claude, not asked):** gimlet's ground holds for everything `build.ts` writes,
so a built site can still be published, compared, or read from `file://` as a
projection of one commit. The dev server already listens only on localhost, and it's
where a person sits while a plan is being written. It re-reads the draft and its notes
on every request to `draft/`, so refreshing the page is the update. Every page links
`draft/` while one exists.

## Decision: The draft page says it's the working tree, not a commit
- where: `src/render.ts`
- quote: `Generated from <span itemprop="repository">${esc(site.repoName)}</span>`

**Because (gimlet, then Claude):** gimlet's "every page says which repo and commit it
was generated from" exists so a reader can tell what they're looking at. The draft page
says "draft, not committed, read at <time>", plus its notes file's hash when it has
one, so an annotation can say which version it answered. Its anchors still resolve at
commits: its `base:` and the commit being served. Jeff: the right default, and likely
forever, but keep watching that it doesn't turn draconian.

## Decision: A draft's open questions use the annotating agreement's prompts, each with a fallback
- where: `guide.md › Working with plans › Drafts (optional)`

**Because (Jeff, agreed in sorrel's cart):** `Question`, `Select` and `Affirm` are what
annotations.nvim already answers, and the agreement allows them at any heading level,
so `### Question:` sits inside an entry without becoming one. Phoropter adds one line,
`**If unanswered:**`, because silence means proceed; the agreement says a reader that
doesn't know something keeps it. The page shows each prompt with its fallback, and its
answer when the notes have one. Whatever writes the notes only has to follow the
agreement: annotations.nvim now, and perhaps phoropter-tui later, letting a person
annotate inside it or open the draft in `$EDITOR` (Jeff). Phoropter-tui hasn't been
given the annotating conventions yet; its next brief carries them.

This replaces twill's `**Open:** … **If unanswered:**` (Claude, unanswered, so its
fallback): the draft asked, and this plan's own draft was written that way.

## Decision: Annotations are shown after the entry that holds their quote
- where (new): `src/draft.ts`

**Because (Claude, not asked):** an annotation quotes the markdown source, and the page
shows rendered HTML, so placing it beside the exact span means mapping one to the
other. Finding the entry whose source contains the quote is exact enough to read
beside, and simple. A quote that matches nowhere is shown at the top as "quote not
found," not dropped: the source moved under it, which the agreement says shouldn't
happen while notes exist.

## Decision: This repository's instructions say drafts go at the root, and carts are optional
- where: `CLAUDE.md`
- quote: `- **Drafts:** when you're unsure or the shared understanding looks thin`

**Because (Jeff):** phoropter isn't part of loom, and shouldn't be beholden to a
`.loom` directory. Jeff still uses carts to think things through, and a cart's result
is "let's draft a plan from this." CLAUDE.md says so; the guide doesn't mention carts.

## Decline: Annotating in the browser
**Because (Jeff, in sorrel's cart):** the File System Access API would let the page
write a notes file without phoropter's server writing, but it's Chromium-only and not
needed while Jeff annotates in nvim. It comes back if teams that won't use vim are to
use this.

## Decline: Ranking what else is anchored at the draft's places
**Because (Claude, not asked):** phoropter-tui's brief asks, for each place a draft
names, what already stands there: unanswered guesses, declines, decisions it would
change, drift. Each anchor already links its place page, which lists those plans. The
ranking is reasoning that deserves its own plan once there's a draft to try it on.
Neither a plain "also anchored here" list nor the ranked one comes into this plan
(Claude, unanswered, so its fallback); the ranking goes on the shelf.

## Guess: Jeff will read a draft on the page, and annotate it beside it
**Disproved if:** after a few drafts, he reads them only in his editor and the page goes
unopened. Then the file is the edge, not the page, and what's worth keeping from this
plan is the one-draft rule and the prompt format. What annotates may change (nvim now,
perhaps phoropter-tui later); the mechanism, a notes file beside the draft, doesn't
(Jeff).
